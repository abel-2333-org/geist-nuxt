## 各组件结论

### foundation-split-pane — modified(status: verified)

**修复(本轮落地)**:

1. **Shift 粗步进**:`SplitPaneHandle` 的 `step(delta, coarse)` 事件把 Shift 意图交给父组件定步长(reference:「`coarse` 只表达 Shift 意图,具体步长仍由父组件决定」),但此前只有 SidebarNav(16→48px)消费了 `coarse`,SplitPane 丢弃第二参数——同一把手在侧栏上 Shift 加速、在分栏上无效,键盘行为系统内不一致。现以 3× 步长响应(ratio 0.04→0.12、fixed 24→72px),与 SidebarNav 惯例对齐。依据:Web Interface Guidelines 键盘可达性 + 设计系统同一 affordance 行为一致性;`coarse` 参数本就是上轮为此语义新增的公开契约。
2. **非法 `aria-valuemax="Infinity"`**:fixed 模式无 `maxSize` 且容器尚未测量(RO 未投递)时 `maxClamp` 回退 `Number.POSITIVE_INFINITY`,`Math.round(Infinity)` 直接渲染为 `aria-valuemax="Infinity"`——ARIA 要求数值。已用 DOM 黑盒测试先行复现(mount 无 `maxSize` → attribute 为 `"Infinity"`),修复为回退当前值(唯一可担保的边界),真实 clamp 测得后自动更新;不选择省略 attribute,因 separator 的隐式 `aria-valuemax` 默认 100,会与 `aria-valuenow`(如 320)矛盾。

**行为契约复核(未变)**:SSR 恒 stacked + 挂载后翻转的断点门控、`useRafTask` 合帧测量(避免 RO 同步反馈环)、MDC 友好的纯字面量 prop、sticky 视口高把手、cookie+useState 持久化、Escape 取消回滚——均与 `split-pane-handle.spec.ts`(SplitPane 关系测试)、`use-split-pane.spec.ts` 及 references 一致。

**新增测试**:fixed 模式 Shift 3× 步进(aria-valuenow 320→344→416);未测量时 `aria-valuemax` 等于 `aria-valuenow` 且为有限数值。

## 为什么没改某些看起来可改的

- **references 两个 index 文件未动**:`references/kits/api-docs/index.md` 在 12 个计划外 item 的 scope-v1 证据内、`references/components/index.md` 在 `foundation-copy-button` 的 scope 内,任何编辑都会把它们拉成 required co-review owner。经逐条核对,两处措辞在本轮改动后仍然准确(「具体步长仍由父组件决定」「各栏不低于 minPane」),无事实漂移,故刻意不touch——文档增补(如显式记录三消费方的 3× 惯例)留给下一次本就要动这些文件的轮次顺手做。
- **SplitPane stacked 分支的 `stackedStart` class**:stacked 分支是普通块级流,`min-w-0`/`min-h-0` 在其中理论上是 no-op;但 SplitPane 根元素接受 fallthrough class,消费方可能把 stacked 容器变成 flex 布局,该防御性 class 届时生效。删除属无收益 churn,不动。
- **`enabledFrom` 类型不对称**(SplitPane 支持 `'always'` 不含 `'2xl'`;CodeRail 反之):CodeRail 的 gate 必须与外层 SplitPane 同步,SplitPane 不支持 `2xl` 则 CodeRail 的 `2xl` 无实际配对场景,而 CodeRail 加 `'always'` 会绕过 stacked 回退。统一类型是公开 API 面变化且无消费者需求,不动。
- **步长常量(24px/0.04/16px 等)**:各消费方的领域步长本就是「父组件决定」契约的一部分,不抽共享常量——抽了反而把领域决策误标为系统不变量。
