## foundation-inline-markdown — improved

`foundation/components/InlineMarkdown.vue`（96 行）。registry description 自称
"Safe inline markdown subset"，而它是 5 个 item 的公共入口：doc author 写进
`description` / `condition` / `notes[].text` / `lifecycle.description` /
enum 行的每一个字符串都经过它。**它的解析规则就是公开契约。**

### 改了什么：标记游程被半吞，裸露标记漏进已发布文档

对 tokenizer 做了输入探测（51 条真实 API 文案形态），发现 4 类输入会让规则表
**只吃掉标记游程的一部分**，剩下的标记字符原样渲染到页面上：

| 输入 | 改前渲染 | 改后 |
|---|---|---|
| `***bold em***` | `<strong>*bold em</strong>*` | `<strong><em>bold em</em></strong>` |
| `__bold__` | `<em>_bold</em>_` | `<strong>bold</strong>` |
| `___all___` | `<em>__all</em>__` | `<strong><em>all</em></strong>` |
| `MAX__VALUE__LIMIT` | `MAX_<em>VALUE</em>_LIMIT` | 字面输出 |

根因是规则表只为「2 标记 vs 1 标记」建立了顺序（`**` 排在 `*` 前），从没有 3 标记规则；
`_` 家族的边界类 `[A-Za-z0-9]` 又不含 `_` 本身，于是标识符里的双下划线被当成一对
emphasis 分隔符。最后一行尤其要命：`MAX__VALUE__LIMIT`、`[a-z_]__[0-9]` 这类
标识符和正则片段在 API 约束文案里到处都是。

修法（`InlineMarkdown.vue:43-92`）：

1. 补 `***…***` 与 `___…___` → ProseStrong 包 ProseEm；
2. 补 `__…__` → ProseStrong（CommonMark strong 的下划线形式，此前完全缺失）；
3. `_` 家族的边界类扩为 `[A-Za-z0-9_]`，即 `_` 自身计入词边界；
4. 同一标记字符**最长游程优先**写成规则表的显式不变量并注释——这不是偏好而是
   正确性要求，短规则先命中就一定会留下多余标记。

依据：`component-reflow.md` §3「命名契约而非内容」——组件对外承诺的是「安全的
行内子集」，吐出 `<strong>*x</strong>*` 是对作者文案的破坏，不是降级；
web-interface-guidelines「Handle empty states—don't render broken UI」同理。
`SKILL.md`「用户内容通过 props / slots」——用户内容必须原样或正确渲染，不能被
渲染器改写。

**非破坏性**：props / emits / slots 未动，纯粹是更多输入被正确渲染。改前能正确
渲染的 40 条形态逐条回归验证，全部不变。

### 新增测试：`tests/component/inline-markdown.spec.ts`（36 例）

此前这个被依赖最多的 foundation 原子**零测试覆盖**，而它的正则带 lookbehind
数字守卫、词边界守卫、平局顺序等一堆微妙语义。新 spec 锁定：

- 6 种标记各自的 Prose 映射、三标记的 strong>em 嵌套；
- 递归嵌套 + code span 永不二次解析；
- 内链走客户端路由 / 外链 `target=_blank` 且 `rel` 含 `noopener`（断言 ULink 真的把
  rel 送到了，而不是只信注释）；
- **18 条技术文本逐字验证**（`snake_case`、`MAX__VALUE__LIMIT`、`^\d{3}\*$`、
  `C:\*.txt`、`[a-z_]__[0-9]`、`1_000_000`、`2*3*4`…）；
- **「绝不残留裸标记」回归族**：10 条输入断言渲染结果不含 `[*_~]`。

### 同步更新的契约面

- `references/components/data-display.md` §InlineMarkdown——支持的子集变了，
  reference 是契约真源（AGENTS.md「设计规则仍以 `references/**` 为准」），必须跟着改。
  补了「不吃技术文本」这条安全属性和已知边界。
- `app/components/gallery/DataDisplay.vue`——gallery 是「活的可视镜像」
  （SKILL.md）。第一个 example 加 `***both***`；新增第二个 example 演示
  **安全属性**（技术文本原样输出），因为对 API 文案消费者来说这比语法表更重要。

### 为什么没改这些

- **不加反斜杠转义（`\*`）**：看起来是缺口——目前 `\*x\*` 会渲染出裸反斜杠。
  但 API 约束文案里正则和通配是常客（`^\d{3}\*$`、`C:\*.txt`），转义规则会把这些
  反斜杠悄悄吃掉，代价大于收益。已把这个取舍写进组件 docstring 和 reference，
  逃生舱是 code span（内容永不解析）。
- **不给 `tokenize` 加 `computed` 记忆化**：一开始判断为性能优化点（一次 anchor
  导航会让全页 FieldItem 重渲染），核查后撤销——FieldItem 是编译模板，
  `<InlineMarkdown :text="…">` 带 PROPS patchFlag，`text` 不变时
  `shouldUpdateComponent` 直接返回 false，子组件根本不会重渲染。加 computed 收益为零，
  属于无谓 churn。
- **不改用 `<script setup>`**：递归产出 VNode 必须用 `h()`，render function 形式是
  正当例外，docstring 已说明。

## api-docs-field-item — improved

`kits/api-docs/components/FieldItem.vue`(528) + `composables/useFieldAnchor.ts`(380)
+ `utils/field.ts`(277)。这是仓库里最重的一个切片，被
`api-docs-schema-composition` 和 `api-docs-field-annotation` 依赖。

整体质量很高——a11y（动态 aria-label、focus-visible、图标 `aria-hidden`）、
语义 token（无硬编码色值 / 圆角）、reduced-motion（`main.css` 全局兜底 +
`useFieldAnchor` 显式 `matchMedia` 判断）、container query 响应式都已达标。
改动只有两处，都很小。

### 1. 长文本溢出守卫在镜像分支上漏了

lifecycle detail 有两份**同样的标记、放在两个位置**：deprecated 走「gate」路径
（描述之上，`FieldItem.vue:324-336`），new/beta 走 secondary band 末尾
（`:462-473`）。两个 `<dl>` 分支类名完全一致，但两个 `<p>` fallback 分支
**漂移了**——new/beta 那份有 `wrap-anywhere min-w-0`，deprecated 那份没有。

后果：deprecated 字段的迁移说明里若含长不断词（升级 URL、替代标识符），在窄容器
下会溢出行；同样内容标成 beta 就正常换行。这正是复制粘贴式重复已经产出实际
分歧的证据。

修法：补齐 deprecated 分支的 `wrap-anywhere min-w-0`，并加注释标明这是一对镜像
分支、必须同步。依据：`references/foundations/responsiveness.md` 的测量式溢出约定，
web-interface-guidelines「Text containers handle long content」。

配套测试 `tests/component/field-item-structure.spec.ts` 新增
`FieldItem lifecycle detail` 两例，参数化跑 deprecated / beta / new，锁住两个位置的
overflow 守卫和 since 行对齐，防止再次漂移。

### 2. 公开数据契约把 auto-expand 机制写错了

`FieldNode.path` 的 docstring（`utils/field.ts:62-66`）、`useFieldAnchor` 头注释
（`:8`）、`FieldItem` 注释（`:98`）三处都写「prefix match」。实现不是——
`childPaths = collectFieldPaths(props.children)` 之后做 `includes()`，是**集合成员
判定**，不是字符串前缀。

这不是措辞问题：`path` 是导出类型的公开字段，那句话让消费者以为
「必须用下划线分隔的层级 id，否则子行不会自动展开」。实际上 FieldItem 只要求
**唯一**。真正依赖下划线前缀的是 `ApiDocsSchemaComposition`（按最长
`active.startsWith(path + '_')` 揭示隐藏 variant，见
`references/kits/api-docs/schema-composition.md:44`——reference 一直是对的，
源码注释才是漂的）。原文把两套机制混成一套，还挂到了错的组件上。

修法：三处注释按实际机制改写，并在 `path` docstring 里分清「FieldItem 只要唯一」
与「同时走 composition 渲染时才需要下划线约定」。依据：`component-reflow.md` §4
「props / emits / slots 契约是否清晰」。

### 为什么没改这些

- **不抽 `<FactRow>` 原子**：`grid-cols-[fit-content(8rem)_minmax(0,1fr)]` 的
  「LABEL + 值」行文法在 FieldItem 里出现 4 次，看着该抽。查了全仓——这个文法
  **只在 FieldItem 内部使用**，EnumTable / SchemaComposition / FieldAnnotation
  都没有。抽成 kit 组件要新增 registry item + files + reference 文档，让每个
  copy-in 消费者多拉一个文件，而 `component-reflow.md` §1 的采纳标准是
  「Nuxt UI 或现有 registry item 没有现成能力，**也无法简单组合**」——一个带
  grid 类的 `<dl>` 恰恰是简单组合。跨组件复用出现之前不抽。已改为消除实际分歧
  （见上）+ 注释标记镜像关系。
- **不拆 528 行 SFC**：vue-best-practices 的拆分触发器（3+ 独立 UI 区块）确实命中。
  但这些区块共享 `t` / `isDeprecated` / `requiredState` / `anchor` 一整组派生状态，
  拆出去要么把它们全部作为 props 逐层传，要么起 provide/inject——两条路都比现状
  更难读，而且会把内部结构变成 registry 的文件边界。文件长度主要来自设计决策
  注释（大量「为什么这样排版」的论证），不是逻辑密度。记为观察项，不动。
- **不改 `:unmount-on-hide="false"`**：全树常驻 DOM，大 spec 页面上是真实开销，
  但它同时保证了 Ctrl+F 可搜和 deep-link 目标必定存在。递归 disclosure 树也无法
  简单虚拟化。属于需要人工权衡的取舍，不在本次单方面改。
- **registry 闭包无冗余**：核查了 `useFieldAnchor` / `field.ts` 的全部消费者——
  `FieldAnnotation`、`SchemaComposition`、`useFieldSource` 都已声明
  `api-docs-field-item`，其余引用都在根 `app/`（不参与分发）。
  `foundation/utils/annotation.ts` 里的 `FieldNode` 只是注释提及，不是 import，
  没有 foundation → kit 越界。三文件打包成一个 item 是对的，无需拆分。

2. **`foundation-inline-markdown`（deferred，带入下次）**：内层标记与外层收尾标记

   delimiter-run 那一档，与第 2 条一起处理。
